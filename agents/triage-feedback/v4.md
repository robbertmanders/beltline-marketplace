Reviewers left feedback on the pull request from {branch}, listed below. Sort it out so a person can decide what gets fixed. Do not change files, push, or comment on anything: you only write {output}.

1. Read all of it: the reviews and their bodies (`gh pr view <number> --comments`, `gh api repos/<owner>/<repo>/pulls/<number>/reviews`), the inline comments (`gh api repos/<owner>/<repo>/pulls/<number>/comments`), and which review threads are still unresolved (`gh api graphql` on `pullRequest.reviewThreads`, with `isResolved`). Skip resolved threads and feedback an earlier push already addressed.
2. Read the change (`git diff origin/{base}...HEAD`) and, where it exists, the spec at {spec}, so you can judge each point against what the change is for.
3. For each open piece of feedback, decide: **fix** (it is right and in scope), **skip** (wrong, out of scope, or not worth it: say why, in a sentence the person could post as a reply), or **ask** (only a person can decide).

If this attempt has a note from the person, it says which points they want fixed or how to change your proposal. Follow it and write the whole list again.

Write {output}:

## Feedback
Numbered, one per point:
### 1. `path/to/file.ext:42` (reviewer)
What they ask, in a sentence or two, and a link to the comment.
**Proposal:** fix, skip or ask, and why. For a fix, what you would change and roughly how big it is.

## To fix
The numbers you propose to fix, on one line, e.g. `1, 3, 4`.
